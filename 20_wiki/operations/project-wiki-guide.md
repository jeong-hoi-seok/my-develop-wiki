# 개별 프로젝트 위키 생성 및 작성 가이드

## 한 줄 요약

소비 프로젝트는 `docs/worklog/`에 작업 맥락을 남기고, 원문이 필요하면 `docs/raw/`를 사용합니다. 작성 단위·메타데이터·AI 조회 순서는 [[worklog-writing-guide]]가 기준입니다.

## 도입과 작업 흐름

1. 프로젝트 `AGENTS.md`와 실제 기록 경로·형식 확인. 구버전 단일 파일·날짜별 파일·옛 메타데이터·신구 형식 혼재 여부 점검. 프로젝트 규칙 우선 적용.
2. 위키가 없으면 도입, 구버전이 있으면 아래 마이그레이션 범위를 확인. 해당 도입·전환이 사용자 요청이나 프로젝트 규칙으로 이미 승인된 경우 재확인 없음. 기존 기록 사용 승인만으로 형식 전환까지 승인됐다고 해석하지 않음.
3. 도입 시 `docs/worklog/README.md` 필수 생성과 프로젝트 지침의 기록 경로 갱신. 도입을 거절한 프로젝트에 기록 체계 생성·수정 없음.
4. 작업 시작 시 관련 코드 확인, 필요한 작업 맥락만 검색. 전체 로그 선행 읽기 없음.
5. [[worklog-writing-guide]]의 기록 대상 결과가 있으면 현재 변경 단위의 기록 작성·갱신. 단순 조회는 제외. 도입 후 매 기록 파일 생성에 별도 승인 불필요.

## 구조

```text
docs/
├── worklog/
│   ├── README.md
│   └── YYYY-MM/
│       └── YYYY-MM-DD-<주제>-<식별자>.md
└── raw/
    └── YYYY-MM-DD-주제.md
```

저장소 루트 `README.md`는 프로젝트 소개, 기록 폴더 루트 `docs/worklog/README.md`는 작성·조회 안내로 둘 다 필수입니다. 서로 대체하지 않습니다. 기록 안내에는 목록이나 매번 갱신할 요약을 두지 않습니다. 월별 폴더·기록 파일은 첫 기록 시 생성합니다.

안내 파일의 최소 내용:

```markdown
# 작업 기록

- 작성·조회 기준: 프로젝트 루트의 `my-develop-wiki/20_wiki/operations/worklog-writing-guide.md`.
- 위치: `docs/worklog/YYYY-MM/YYYY-MM-DD-<주제>-<식별자>.md`. MR/PR 하나당 기록 하나가 기본.
- 조회: 주제·코드 경로로 관련 기록을 찾고, 참조된 이전 기록과 이를 대체한 후속 기록 확인.
```

## 구버전 worklog 마이그레이션

기본 전환은 **병합된 과거 기록은 원래 위치에 보존하고, 미병합 기록과 이후 기록만 새 형식으로 옮기는 방식**입니다. 과거 전체를 월별 파일로 재분류·요약하지 않습니다. 과거 기록까지 변환하려면 별도 범위 합의와 원문·참조 보존 검증이 필요합니다.

1. **감지·경계 확인**: 지침에 적힌 경로와 실제 파일을 확인. `docs/worklog.md`, 날짜별 로그, 현재 9개 필드와 다른 기록이 대상. 대상 브랜치와의 diff·Git 이력으로 병합된 과거와 현재 브랜치의 미병합 추가·수정을 구분. 날짜나 파일 존재만으로 판별하지 않으며 Git 근거가 없거나 불명확하면 확인 전 삭제·이동 없음.
2. **기준 보존**: 전환 전 파일·항목·기여자·원문 참조와 비교할 Git 커밋을 기록. 미커밋 항목은 검증이 끝날 때까지 원문 유지. 이미 병합된 본문·작성일·작성자·기존 id·경로는 변경하지 않음. 보존 안내만 추가 가능.
3. **미병합 기록 이동**: 현재 변경의 새 worklog 하나로 옮기되 이미 옮긴 항목은 재사용. 이전 경로·항목 날짜·제목을 남기고 내용·결정·검증 한계 보존. 기존 항목을 수정하던 작업이면 병합된 원문은 유지하고 정정 내용만 새 기록에 작성. 일치 검증 후 해당 브랜치의 미병합 추가·수정만 옛 파일에서 제거. 전체 파일 삭제·다른 사람의 기록 재작성 없음.
4. **새 메타데이터 구성**: 새 파일의 `created_at`은 새 기록 파일 생성일, 원래 사건 날짜는 본문에 보존. 실제 기여자 확인, 새 id 발급 전 중복 확인. 신형으로 이미 전환된 기록의 id·생성일은 유지. 옛 id·경로 참조는 본문으로 추적하고 `related`에는 신형 기록의 실제 id만 사용. 불명확한 작성자·날짜를 추정해 채우지 않음.
5. **쓰기 경로 전환**: 필수 README와 프로젝트 지침에 전환일·새 경로·모든 구버전 위치·추가 작성 종료를 명시. 진행 중인 다른 작업 브랜치에도 같은 전환 기준 적용. 구버전 파일이 없어질 때까지 기다리지 않고 과거 조회에 계속 포함. 재실행 시 안내·이관 기록을 확인해 중복 파일을 만들지 않음.
6. **완료 검증**: 전환 전후 병합된 본문 일치, 옮긴 항목 누락·중복 없음, 새 필수 필드·id·관계·원문 링크 확인. 새 기록과 구버전, 존재하는 raw 원문 모두에서 관련 맥락을 찾을 수 있어야 완료. 실패하면 옛 항목 제거를 진행하지 않고 누락을 해결.

위키 가이드 수정만으로 소비 프로젝트 파일을 일괄 이관하지 않습니다. 기존 프로젝트는 자체 지침을 갱신하면서 전환합니다. 파일명 변경만 하는 작업이 아니라 쓰기 경로·메타데이터·과거 조회를 함께 전환합니다.

**과거 전체 이관을 별도로 요청한 경우**: 기존 항목 단위를 유지해 원문·사건 날짜·작성자·collapsed 표기를 새 파일로 복사합니다. 이미 묶인 과거 항목을 추측으로 MR별 분해하지 않습니다. `created_at`은 새 파일 이관일이며, 파일명 날짜·월 폴더는 [[worklog-writing-guide]]의 사건 날짜 기준을 따릅니다. 원문 일치·누락·중복·참조 검증 후 옛 파일은 추가 작성이 없는 안내로 유지합니다. 구버전 파일 삭제도 사용자가 요청하면 모든 참조를 새 경로로 갱신한 뒤 삭제합니다. 이관된 과거 기록은 후속 작업으로 덮어쓰지 않습니다.

## 운영 기준

- 원본 보존과 선택적 조회가 기본. 작업 완료 시 주간·월간 자동 compact 의무 없음.
- 월별 폴더는 총 파일 수를 제한하지 않음. 파일 증가량·검색 시간·AI 조회량은 적용 후 측정.
- 아카이브는 실제 비용이 문제일 때 검토. 도입 전 실행 시점·담당 자동화·진행 중 브랜치 처리·원본 및 참조 보존 설계.
- `docs/worklog/`의 앱 import·배포 자산·업로드 입력 포함 여부를 확인하고 불필요한 포함 제외. 앱 배포 경로에 기록 보관 금지.
- 포맷·문서 검사는 필요한 기록 범위만 처리하도록 확인. Git 보관·checkout 비용까지 없어지는 것은 아님.

## 도입 시 검증

- 여러 작업 브랜치를 쓰는 프로젝트는 독립 기록의 경로·식별자가 겹치지 않는지 확인
- `scope`·코드 경로로 과거 기록과 이를 대체한 후속 기록, 연결된 raw 원문까지 조회 가능한지 확인
- 실제 기여자·미수행 검증·남은 일의 누락·과장 여부 확인
- 소비 프로젝트 빌드·배포 입력에서 기록 제외 여부 확인

이 항목들은 도입 시 검증 기준입니다. 가이드 작성만으로 브랜치 간 병합·조회 비용·빌드 영향을 검증한 것으로 보지 않습니다.

## raw/ (선택)

회의록·메모·긴 대화 로그처럼 나중에 다시 검증할 원문만 보관한다.

- 수정하지 않는다. 거칠어도 원문성 유지.
- **평면 구조**, 파일명 `YYYY-MM-DD-주제.md`.
- 보안 정보·토큰·개인정보 금지. 필요하면 마스킹.
