# 프로젝트 작업 기록 가이드

## 한 줄 요약

작업 기록은 `docs/worklog/YYYY-MM/YYYY-MM-DD-<주제>-<식별자>.md`에 변경 단위로 남깁니다. 기본 단위는 MR/PR 하나이며, AI는 관련 기록만 검색해 읽습니다.

## 적용 범위와 기록 단위

나중의 나와 AI가 작업 이유를 다시 찾기 위한 개인 프로젝트 기준입니다. 날짜별 일기 대신 변경 단위로 기록하고, 여러 브랜치의 기록도 분리합니다. 도입·필수 README·기존 로그 전환은 [[project-wiki-guide]], my-develop-wiki 자체 적용은 [[log-writing-guide]]를 따릅니다.

```text
docs/
├── worklog/
│   ├── README.md                          # 필수 고정 작성·조회 안내
│   └── YYYY-MM/                          # 파일명 날짜의 월
│       ├── 2026-09-21-save-validation-a81f3c92.md    # 변경 단위별 기록
│       └── 2026-09-22-image-cache-b62d914e.md
└── raw/                                 # 필요한 원문만 보관
```

- 파일: `YYYY-MM-DD-<주제>-<식별자>.md`. 날짜·소문자 kebab-case 주제·랜덤 8자리 소문자 16진수 식별자 순서. 생성 전 파일명·`id` 중복 확인, 충돌하면 식별자 재생성.
- 날짜·폴더: 새 기록은 최초 기록일인 `created_at`, 과거 이관 기록은 원문의 사건 날짜 사용. 기간 기록은 시작일 사용. 원문 날짜를 확인할 수 없으면 추정하지 않고 이관일을 사용한 이유를 본문에 명시. 월 폴더는 파일명 날짜의 `YYYY-MM`과 일치. 후속 수정으로 날짜·폴더를 바꾸지 않음.
- MR/PR 하나당 기록 파일 하나가 기본. MR이 없어도 작업 브랜치의 독립 변경 단위로 시작. 날짜·커밋·AI 응답마다 파일 생성 금지.
- MR 분할·통합 시 아직 병합되지 않은 해당 변경의 기록만 범위에 맞춰 분리·통합하고 기존 참조 확인. 이미 병합된 기록은 보존.
- `dev` → `main`처럼 병합된 변경을 모으는 릴리즈 MR은 기존 기록을 참조. MR 생성만을 이유로 기록을 합치거나 중복 생성하지 않음. 새로운 릴리즈 결정·검증이 있으면 그 내용만 별도 기록.
- 독립 MR 사이에서는 기록 파일 공유 없음. 같은 MR을 공동 작업하면 같은 기록의 충돌은 여전히 가능.

## 메타데이터

작업 기록에는 아래 필드만 필수로 둡니다. [[wiki-authoring-guide]]의 전체 frontmatter와 `audit_log`는 적용하지 않습니다. `README.md`는 안내 파일이므로 기록용 frontmatter도 필요하지 않습니다.

| 필드 | 형식 | 작성 기준 |
|---|---|---|
| `id` | `worklog-<식별자>` | 파일명 끝 식별자와 일치. 생성 후 고정 |
| `title` | 문자열 | 핵심 변경을 나타내는 한국어 제목 |
| `scope` | 소문자 kebab-case 문자열 하나 | 주된 영역. `auth`, `slot-editor` 등 프로젝트 명칭 사용. 나머지 영역은 경로·본문으로 설명 |
| `authors` | 문자열 목록 | 실제 작업 기여자를 Git 작성자·작업 맥락으로 확인. 문서 편집자·AI 모델명으로 대체하거나 추정 금지. 기여 구분은 필요 시 본문 기재 |
| `created_at` | `YYYY-MM-DD` | 최초 기록일. 생성 후 고정 |
| `updated_at` | `YYYY-MM-DD` | 마지막 내용 수정일. 단순 조회 시 변경 없음 |
| `topics` | 문자열 목록 | `validation`, `cache`처럼 영역을 가로지르는 검색어. 없으면 `[]` |
| `code_paths` | 문자열 목록 | 저장소 루트 기준 핵심 파일·디렉터리. 관련 코드가 없으면 `[]` |
| `related` | `{id, relation}` 객체 목록 | 다른 작업 기록 참조. 없으면 `[]` |

영역·주제는 기존 값을 재사용하되 별도 분류표를 매번 갱신하지 않습니다. 날짜는 프로젝트 시간대 기준이며, 미지정 시 Asia/Seoul을 사용합니다.

선택 필드는 `mr_url`과 `issue_urls`입니다. 실제 주소가 생긴 뒤 추가하며, 기록만 보완하려고 MR을 생성하지 않습니다. 브랜치명·병합 상태·빌드 상태는 필수 필드로 복제하지 않습니다.

`relation`은 `related` 참고·`supersedes` 결정 대체·`resolves` 후속 과제 해결 중 하나입니다. 본문에 참고 맥락, 대체 대상·이유, 해결 대상·검증 결과를 각각 명시합니다. 새 기록에서 이전 기록으로만 선언하며, 이전 파일의 역방향 링크 갱신은 없습니다. 관계의 효력은 명시한 대상에 한정합니다.

## 본문 작성 기준

**한 줄 요약이나 고정 분량을 강제하지 않습니다. 나중의 나·AI가 판단을 재구성할 만큼 맥락을 남깁니다.**

- 기본 구성은 `변경과 이유`, `검증과 한계`. 복잡한 작업은 문제 상황·제약·선택 근거·검토한 대안·결과를 여러 문단으로 설명. 남은 일·결정 변경은 있을 때 추가.
- 코드만으로 알기 어려운 이유와 검증 범위 보존. 확인된 사실만 기록하고 미수행 검증은 명시. 불확실은 `[검증 필요]`, 추론은 `[추론]` 표시.
- 근거로 사용한 회의록·원문이 있으면 본문에 경로·날짜·제목을 남겨 다시 조회 가능하게 작성. 원문 전체를 기록에 복사하지 않음.
- 커밋 목록·전체 diff·명령 이력·MR/PR 설명의 반복 복사 생략. MR/PR 작성은 [[mr-pr-guide]] 적용.
- 토큰 절약은 본문을 억지로 줄이기보다 관련 기록의 선택적 조회로 해결. 짧은 예시는 분량 제한이 아님.

## 작성 예시

아래는 형식 설명용 예시이며 실제 프로젝트 검증 결과가 아닙니다.

```markdown
---
id: worklog-a81f3c92
title: 슬롯 저장 유효성 검사
scope: slot-editor
authors: [정회석]
created_at: 2026-09-21
updated_at: 2026-09-21
topics: [validation, error-message]
code_paths:
  - src/features/slot-editor/
related: []
---

# 슬롯 저장 유효성 검사

## 변경과 이유

- 필수값 누락 시 저장 차단과 입력 오류 표시 추가
- 사용자가 저장 실패 이유를 확인할 수 없던 문제 해결

## 검증과 한계

- 필수값 누락·정상 저장 테스트 통과
- 실제 브라우저 검증 미수행
```

## 작성 시점과 병합 후 관리

1. 먼저 기록할 결과가 있는지 확인. 단순 조회·설명·상태 확인과 기존 결론 반복은 파일 생성·수정 없음. 실제 변경, 채택된 결정, 새 검증 결과, 후속 조치가 필요한 발견 사항은 기록. 사용자가 답변 저장을 요청한 경우도 포함.
2. 같은 변경의 미병합 기록이 있으면 재사용. 독립 조사·결정도 확정된 결과가 있으면 하나의 기록 단위로 묶음. 여러 날도 같은 파일 사용. 중복 설명은 기존 항목에 반영, 별도 사건·후속 결과는 날짜를 붙여 아래에 추가. 임시 계획·진행 중 생각은 누적하지 않음.
3. MR/PR 제출 전 기록과 실제 diff의 범위 확인. 필수 필드·식별자 중복·관계 대상 존재 여부 확인.
4. 병합 완료 후 기록 보존. 정정·추가 검증·후속 변경은 새 기록에서 이전 기록 참조.

장기 추적 과제는 이슈로 연결하고, 공용 미해결 목록을 매번 수정하지 않습니다.

## AI 조회 순서

1. 현재 정책은 프로젝트 `AGENTS.md`·규칙 문서, 현재 동작은 코드·테스트로 확인. 로그는 당시 판단·검증의 근거로 사용.
2. 과거 맥락이 필요하면 `scope`·`topics`·`code_paths`로 후보 검색. 날짜는 보조 기준, 작성자는 기여 추적 시 사용.
3. 후보의 제목·메타데이터를 확인한 뒤 관련 본문만 읽기. 오래된 중요한 기록도 포함.
4. `related` 대상을 확인하고, 선택한 기록의 `id`를 참조하는 후속 기록도 검색. 대체·해결 관계가 적용되는 범위와 근거 확인.
5. 선택한 기록을 과거 → 최신 순서로 읽되, 현재 코드·규칙과 대조. 작성일만으로 병합 순서나 현재 적용 상태 추정 금지.

검색이 부족하면 본문 키워드·옛 경로·기존 로그까지 확대합니다. 기록만으로 판단 근거가 부족하거나 서로 충돌하면 연결된 원문을 확인합니다. 연결이 없으면 프로젝트 `docs/raw/` 또는 지침에 정한 원문 위치에서 관련 자료만 검색합니다. 원문도 없으면 추정하지 않고 확인할 수 없는 범위를 명시합니다. 검색 실패를 기록 부재로 단정하거나 전체 로그·최근 N개·raw 전체를 매번 선행 학습하지 않습니다.

## 보관과 도입 검증

원본을 보존하며 작업 완료 시 자동 compact를 요구하지 않습니다. 파일 누적량·아카이브·빌드 제외·조회 검증은 [[project-wiki-guide]]의 운영 기준을 따릅니다.
